# Music Genre Concept-Bottleneck Model

This is a jointly trained PyTorch concept-bottleneck model for multilabel music
genre classification. A shared log-Mel CNN feeds instrument, rhythm, timbre, and
harmony branches. Their predicted concepts are fused to predict six genres.

## Results

| Split | Tracks | Genre macro average precision |
|---|---:|---:|
| Validation | 1,099 | 0.6804 |
| Test | 1,098 | 0.6781 |

The selected checkpoint is from epoch 10. Test binary cross-entropy loss was
0.3310. The split contains 5,127 training tracks, 1,099 validation tracks, and
1,098 test tracks.

These metrics are from one training run and should not be interpreted as a broad
benchmark against other systems.

## Outputs

The genre order is:

```text
classical, electronic, folk, hiphop, jazz, rock
```

The checkpoint also contains the 41-instrument vocabulary, timbre and rhythm
standardizers, branch weights, fusion weights, and preprocessing metadata.

## Input preprocessing

- Sample rate: 16,000 Hz
- Log-Mel bands: 128
- Hop length: 512 samples
- Window duration: 15 seconds
- Centered STFT: yes
- Maximum sampled windows per track: 12
- Window frame capacity used by the trainer: 1,366

Preprocessing must match these values. The model consumes stored log-Mel arrays
and the window masks, valid-frame counts, and window start times generated by the
project data contract.

## Loading the checkpoint

The architecture implementation is maintained in the
[music-genre-classification repository](https://github.com/tharu-jwd/music-genre-classification/tree/ce0fe2d).
Use source revision `ce0fe2d` for exact training-time compatibility.

```python
import torch

checkpoint = torch.load("best.pt", map_location="cpu", weights_only=False)

# State dictionaries available in the checkpoint:
# checkpoint["encoder"]
# checkpoint["instrument_head"]
# checkpoint["rhythm_head"]
# checkpoint["timbre_head"]
# checkpoint["harmony_head"]
# checkpoint["fusion_model"]
```

Instantiate the modules as in `scripts/train_joint.py`, load each corresponding
state dictionary, call `eval()`, and apply a sigmoid to the fusion logits to get
the six genre probabilities. `best.pt` was produced by this project and includes
optimizer state and non-tensor metadata, so only load it from a trusted source.

## Training details

- GPU: NVIDIA L4
- Epochs: 10
- Batch size: 4
- Optimizer: AdamW
- Initial learning rate: 0.0003
- Scheduler: cosine annealing
- Selection metric: validation genre macro average precision
- Source dataset table: `vector-dataset-normalized.csv`

The joint objective combined genre BCE, instrument BCE, rhythm Smooth L1, and
timbre Smooth L1 losses. Targets for continuous branches were standardized using
training-split statistics.

## Important harmony limitation

This training table contained a 12-value harmony descriptor vector, not the
required 12-bin chroma probability target. The harmony auxiliary loss was
therefore masked for every example. The harmony branch still received gradients
through the final genre fusion objective, but this checkpoint does **not** provide
evidence that its harmony predictions are musically accurate.

## Files

- `best.pt`: full training checkpoint and model metadata
- `results.json`: epoch history and final validation/test results
- `config.json`: machine-readable architecture, preprocessing, and label summary

## Intended use and limitations

This checkpoint is intended for research, coursework, reproducibility, and
architecture experiments. It has not been calibrated for production decisions.
Performance may not transfer to music distributions that differ from the training
collection. Instrument, rhythm, and timbre validation metrics were added to the
trainer after this run, so this historical checkpoint only records their training
loss curves; a new run is required for branch-level validation comparisons.
